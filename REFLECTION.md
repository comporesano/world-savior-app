# REFLECTION.md — рефлексия агента

## Что удалось

- **Полный цикл за одну итерацию:** спроектирован и реализован работающий
  продукт — REST API (16 эндпоинтов), SPA-клиент, 35 тестов, демо-данные,
  скриншоты и видео. Всё запускается двумя командами (`pip install`,
  `uvicorn src.main:app`).
- **Авторизация «по-взрослому»:** bcrypt, access+refresh с ротацией,
  refresh-токены в БД только в виде SHA-256-хешей, детект повторного
  использования с отзывом всех сессий — и всё это покрыто тестами.
- **Качество через проверки:** 35 API-тестов зелёные; палитра UI прогнана
  через валидатор CVD/контраста (несколько итераций до прохода всех
  проверок в обеих темах); страницы проверены на отсутствие console-ошибок
  и горизонтальных переполнений.
- **Безопасность как default:** CSP без `unsafe-eval` (из-за него даже
  пришлось переделать демо-скрипты — это правильная цена), rate limiting,
  security-заголовки, экранирование всего пользовательского контента в SPA,
  zod/pydantic-валидация на входе.
- **Честный учёт баллов:** начисление ровно один раз, только организатором,
  только после подтверждения — с проверками в тестах.

## Что не удалось / стоило бы улучшить

- **Смена стека по ходу работы.** Первая версия была на Node.js (Express +
  React + TS): сервер был почти готов и прошёл 28/35 тестов, когда
  пользователь попросил Python. Дизайн-решения удалось перенести (схема БД,
  ротация токенов, уровни), но время на Node-версию потрачено зря. **Вывод
  для практики:** согласовывать стек до начала реализации, а не после.
- **Конкурентные гонки.** Проверка вместимости (`count >= capacity`) и
  подтверждение (`status == 'joined'`) — это check-then-act без блокировок:
  при одновременных запросах возможна перезапись. Для SQLite-демо
  приемлемо, для production нужен `SELECT … FOR UPDATE` или уникальные
  частичные индексы. Зафиксировано в README как улучшение.
- **Клиент не покрыт тестами.** Тестируются только API (35 тестов); логика
  SPA (уровни, форматирование) проверена косвенно через скриншоты и
  E2E-прогон Playwright. Стоило бы добавить минимум юнит-тестов клиентских
  утилит.
- **Отсутствие CI и контейнеризации.** pytest и демо-скрипты запускаются
  локально; GitHub Actions и Docker Compose остались в планах.
- **Уведомления.** Нет email/telegram-оповещений о записи и подтверждении —
  для реального волонтёрского сервиса это ключевая фича.

## Что было неожиданным

- `lower()` в SQLite не работает для кириллицы → поиск регистронезависимым
  пришлось делать через кастомную SQL-функцию `lower_utf8`.
- CSP приложения заблокировал `add_init_script` Playwright — пришлось
  «входить» в демо-сценариях через UI-форму. Это, по сути, подтверждение,
  что CSP реально работает.
- CDN Playwright был недоступен; спас кэш браузеров: версия пакета
  подобрана по ревизиям кэша (playwright 1.58.0 ↔ chromium-1208,
  ffmpeg-1011) через PyPI JSON API.

## Итоговая оценка подхода

Гибрид «спроектируй → реализуй → проверь тестами → покажи скриншотами/видео»
сработал: каждое архитектурное решение подтверждено исполняемыми проверками,
а не обещаниями. Главный урок — **сначала договориться о стеке**, остальное
переносится между стеками почти без потерь.
